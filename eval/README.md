# eval：打分器评测（golden set）

回答一个问题：**这个打分器能不能分出「讲得好」和「讲错了」？**

## 结构

| 文件 | 作用 |
| --- | --- |
| `build_golden.py` | 构造 golden set：5 题 × 3 档 = 15 条答案，输出 `golden.jsonl` |
| `golden.jsonl` | 评测集本体，字段 `id / qid / tier / topic / question / answer / expected_rank` |
| `run.py` | 跑评测，输出排序一致性与分差，结果写 `last-<tag>.json` |

## 分档口径

分档**不按长度**，按「信息完整度 + 机制正确性」：

| 档位 | 定义 | 举例 |
| --- | --- | --- |
| `good` | 机制正确、有取舍理由、有数字，接近 `my/best-answers.md` 的口径 | Q1：Redis 悲观锁按 orderID 串行、StFailed 一等状态、三层存储 |
| `mid` | 方向对但缺关键层：只讲结论不讲理由，或过程偏薄 | Q10：根因讲对了，但没有逐层排除、动作不可执行、时间数字含糊 |
| `bad` | 术语密度高但机制说错，或把监测说成拦截 | Q1 说用 MySQL + 版本号 CAS；Q5 说 MySQL 每 5 秒全表扫；Q10 编造「主从延迟丢 3 万单」 |

`bad` 档是**对抗样本**：它们读起来比 `mid` 更"专业"（术语多、数字具体），专门用来测打分器会不会被术语密度骗。

## 指标

- **rank_ok**：同一题内 `good > mid > bad` 严格成立（打分器最核心的能力）
- **margin**：该题最高分与最低分之差，太小说明分不出好坏
- **covered**：命中要点数，关检索时应为 0，用来确认检索真的被用上

## 跑法

```bash
# 接检索（每题 1 次调用）
LLM_TEMPERATURE=0 .venv/bin/python -m eval.run --tag final

# 关检索做对照，只跑差档
LLM_TEMPERATURE=0 .venv/bin/python -m eval.run --tag off-t0 --no-kb --tiers bad

# 只跑某几题
LLM_TEMPERATURE=0 .venv/bin/python -m eval.run --tag q10 --qids Q10
```

**温度必须设 0**。默认温度下同一份答案两次跑会差 0.8 分（实测 Q8-good 4.50 → 3.70），排序结论会被抖动吃掉。

## 评测过程中改掉的两个真问题

1. **打分器被"伪具体性"骗**
   Q10 的 `bad` 档编造了「主从延迟丢 3 万单，写脚本回补」，读起来比老实但空洞的 `mid` 更像有工程能力，一度 `mid 2.20 < bad 2.40` 倒挂。
   处理：prompt 要求模型输出 `fact_mismatch`，**代码端**在 `scoring.py` 里对该标记封顶总分 2.0（`FACT_MISMATCH_CAP`）。只靠 prompt 里的"不给加分"没用，必须在代码里夹紧。

2. **`mid` 样本自己也不干净**
   修完封顶后 Q10 变成 `mid 2.00 = bad 2.00` 并列，查下来是 `mid` 档把根因也写错了（说成内存泄漏）。改成「口径对、过程薄」后恢复 3.40，排序成立。
   教训：**排序不对时，先怀疑样本，再怀疑打分器。**

## 还没做的

- **人工标注**：`expected_rank` 现在是构造先验，不是你的判断。校准方式很轻：每题看一眼三档答案，给一句「这档我给自己几分」。有偏差就改样本或改 rubic，别改分数。
- **样本量**：5 题 × 3 档只能发现明显问题，不能估置信区间。题目扩到 10 题、每档 2 条独立写法，才谈得上稳定性。
- **多票取中位**：单次打分即便温度 0 仍有 ±0.3 抖动，讲求严格时同一答案跑 3 次取中位（成本 ×3）。
