## 一、模型判断与代码判断必须分层

### 1. 总分不能让模型自己给
**现象**：让模型直接输出 `total`，同一份答案两次给 4.2 和 3.6，且六维分与 total 对不上（加权算出来是 4.05）。

**改法**：模型只出六维分和依据，**总分由 `app/scoring.py` 按固定权重重算**，模型的 total 直接丢弃。六维分再逐项 clamp 到 0–5。

**为什么重要**：一旦总分是模型给的，你无法解释「为什么 4.2 而不是 4.0」，也没法在换模型后保证口径可比。

### 2. 关键约束要写成代码，不能只写进 prompt
**现象**：评测里「编造事故」的回答拿到 2.40，高于老实但空洞的回答 2.20。先在 prompt 加「事实不符不因此加分」——完全无效，仍是 2.40；再加「correctness ≤ 2、engineering ≤ 3」的硬上限，才降到 1.80，但答卷仍能靠 engineering 的保底 3 分撑着。

**改法**：prompt 要求模型输出布尔字段 `fact_mismatch`，代码端 `FACT_MISMATCH_CAP = 2.0` 强制封顶总分。

**结论**：**prompt 是软约束，代码是硬约束**。凡是「绝不允许超过某个值」的规则，都要在代码里夹紧一遍。

## 二、评测集本身比打分器更容易错

### 3. 排序倒挂时先怀疑样本，再怀疑打分器
三次应验：
- Q10 `mid` 把根因写错了（说成内存泄漏），与正确性冲突 → 修样本后 3.40
- Q3 `mid` 写「删除缓存 + 命中率 99% 多」，与本人事实（写前校验、99.95%）冲突 → 修后 2.90
- Q8 `mid` 说用了 checkpointer、权限靠 prompt、做了重排，三样全是反的 → 修后 2.60

**教训**：写 `mid` 档的人（包括我自己）会不自觉地把技术名词填满，把「半懂」写成「全懂」；这类样本本身不干净，用它去调 prompt 会越调越偏。

### 4. 「伪具体性」能骗过 rubric
编造「主从延迟丢 3 万单、写脚本回补两小时」比「我排查了监控盲区」更像有工程能力，因为前者有动作、有数字。

**对策**：数字只有在与事实源一致时才计入 engineering 分；否则整条按事实不符处理。

### 5. 好的样本要真的回答题面
Q8-good 一度答的是编排、SSE、会话、权限，而题面问的是「意图识别与工具调度 / RAG 降噪 / 工具调用治理」——**模型自己把这三块列进了 `missing`**。

**教训**：golden set 里最贵的错误不是「分打错」，是「标准答案本身不对题」。

### 6. 同一份材料里两个数混说
演示稿正文写「4 节点 2 路由」，指标卡写「5 步 · 客服 workflow 节点」，第一版答案把两个数塞进同一句，自相矛盾。

**对策**：数字要能追到唯一出处；两处口径不一致时，先定一个，别并排说。

### 7. 温度不是抖动的全部来源
设 `LLM_TEMPERATURE=0` 后，同一份 Q8-mid 仍出现 2.50 → 1.70。温度能压住采样随机性，压不住「模型对同一段话的读法」。

**现状**：排序稳（5/5 多轮未翻），刻度不稳（±0.3–0.8）。要报精确分必须多票取中位（成本 ×3）。

## 三、检索：便宜的做法也能有净收益，但要能证明

### 8. 关键词召回足够用，前提是零额外调用
把 10 题最佳答案切成按题知识块，用「中文双字 + 英文词 IDF 加权 + 主题词加权」做本地召回，召回结果拼进本来就要发的打分 prompt。

**收益**：10 题召回 10/10；错答案平均再降 0.40，Q1 的 CAS 错误回答 3.30 → 2.00。

**关键设计**：召回为空/低于阈值就**退化成原行为**，知识库缺失不影响主链路；召回只做「覆盖度对照」，不拿来冒充候选人的话。

### 9. 解析器的静默失败比崩溃更贵
两个自引入 bug，都不报错，只表现为 prompt 里塞了乱码 / 少了整段：
- 去 Markdown 项目符号的正则写成 `^[-*]\s*`，把 `**加粗**` 的首个星号吃掉，标签变成 `*模型与分流**` → 改 `^[-*]\s+`
- 小标题带括注（`**边界（最重要）**`）时用原始串匹配字段名，整段静默漏掉 → 先剥离括号内容再匹配

**教训**：**解析类代码要有「解析出 0 个字段就报错」的断言**，否则错误只会往下游漂。

## 四、成本与护栏

### 10. 调用预算要单一收口
所有 LLM 调用走同一个 `BudgetedLLM` 包装，超上限抛 `BudgetExceeded`，绝不无限重试。本次补漏发现 `ask` / `prep` / `chat` 三个命令原本直接用裸 client、没有护栏——**只要有一条路径绕过包装层，护栏就等于没有**。

### 11. 观测要落在同一个收口
`trace.jsonl` 记四类事件：`llm` / `tool` / `kb` / `score`。挂在 `BudgetedLLM.chat()`、工具分发、`kb.retrieve()`、`score_answer()` 四处，命令行/Web/评测三条路径自动全覆盖。

**为什么必须记 `score`**：最终分数是「模型判断 + 代码重算 + 封顶」三段拼出来的，只记最终分无法倒查。

## 五、几条偏产品侧的判断

### 12. 承认缺口应该加分，不该扣分
第一版 rubric 把「承认没做重排 / 没做超时幂等」当成深度不足，等于奖励吹牛；Q8-good 因此卡在 4.10。改成「要点里写明的缺口照实说算命中，depth 只看是否讲清取舍，boundary 主动认边界给 4–5，把没做的说成做了则 boundary 降到 2 以下」，Q8-good 升到 4.50 且排序不变。

**这条是用户拍的，也是这个项目最反直觉的一条**：面试场景里，**诚实本身就是被考核的能力**。

### 13. 评测先做「能分出好坏」，再做「分数准」
P4 的目标不是把分数校准到小数点，而是验证「同一题内 good > mid > bad」成立。5 题 15 条就能暴露打分器的结构性问题（伪具体性、样本不干净、口径混说），成本可控；等排序稳了再谈扩样本与多票取中位。
